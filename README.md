# FlowStudio

安卓上的移动端音乐工作站。自写的 C++17 实时音频引擎 + 全自绘 Kotlin 界面，零第三方依赖。

APK 约 1 MB（含原生引擎）。装到 arm64 手机上直接能编曲。

## 怎么跑

```bash
./tools/build_native.sh   # 交叉编译 C++ 引擎 -> libflowengine.so
./tools/build_apk.sh      # Kotlin -> dex -> aapt2 -> zipalign -> apksigner
adb install build/FlowStudio-1.0.0.apk
```

或者推到 GitHub，Actions 会自动出包（见 `.github/workflows/build.yml`）。

## 1.36 更新

三个用户报的问题，逐个查到根因，都不是表面现象。

### 1. 自定义背景图无法生效

前四轮都在调透明度参数，这次找到了**逻辑上的死结**。

**真因 A：换图时路径不变，加载判据认不出"内容换了"。**

`importBackground` 永远写 `filesDir/theme/background.jpg` —— 固定文件名。
而加载判据是：

```kotlin
val needLoad = shouldShow && (bg.backgroundImage == null || bg.loadedPath != wantPath)
```

第二次选图时 `wantPath` 和 `loadedPath` **是同一个字符串**，`needLoad` 恒为
`false` → 走 else 分支 → 什么都不做。磁盘上的图确实换了，内存里那张位图没换。

**修法（三层）：**

1. 文件名带序列号 `background-1.jpg` / `background-2.jpg`……路径本身就变了，
   任何基于路径比对的逻辑都成立；旧图在写完新图之后删掉，磁盘上始终只有一张。
2. 新增 `backgroundVersion`（每次导入 +1）与 `WallpaperView.loadedVersion`，
   加载判据改成三条件：`backgroundImage == null || loadedPath != wantPath ||
   loadedVersion != wantVer`。版本号是"内容真的变了"的唯一可靠信号。
3. 加载**失败**时清空 `loadedPath` / `loadedVersion`。以前失败不清，
   下次进来 `loadedPath == wantPath` 成立 → 判定"已加载" → 永远不重试。

**真因 B：导航条是一整条实色横条。**

`MainActivity` 里 `bar.setBackgroundColor(Palette.SURFACE)` —— 48dp 实色，
壁纸在这一条上完全不可见。前几轮把工具栏、走带条、标尺都改成了半透明帽，
唯独漏了导航条。

改成 `CanvasBackdrop.chrome(Palette.SURFACE)`，并新增 `refreshChromeTint()`：
这类用 `setBackgroundColor` 上色的原生容器把颜色**烤进了 Drawable**，
不读 `CanvasBackdrop`，开关变化时必须手动重设一次才生效。

**真因 C：`invalidate()` 只标脏自己。**

图异步加载完成后只 `invalidate()` 了 `WallpaperView`，父容器和兄弟视图不会因此重画。
各内容页的 `CanvasBackdrop.showThrough` 是**绘制时**读的，要让每一层重新 `onDraw`
才看得到新底色。现在图到位后逐层 `postInvalidateOnAnimation()`，合并到同一帧。

**顺带补的入口**：设置副标题一直写着"轻点更换或清除"，但从来没有清除这一项。
新增「清除背景图」行，同时删磁盘文件、清 prefs、推进版本号。

### 2. 播放时播放头不动，音轨自己滚

1.35 及之前是 `scrollToPlayheadIfNeeded`：

```kotlin
if (x > w * 0.85f || x < headerWidth) { scrollX = ... }
```

播放头自己在屏幕上从左跑到右，跑到 85% 处被拽回来一屏。观感就是"播放头在动、
音轨不动"—— 正好是要改的那种。

改成每帧解一个方程，让播放头的屏幕 x 恒等于锚点（内容区宽度的 30%）：

```
tickToX(pos) = headerWidth + pos*bw/BAR - scrollX  ≡  锚点x
⇒ scrollX = pos*bw/BAR - (内容宽 × 0.30)
```

`scrollX` 为负时钳到 0 —— 曲子开头那几小节画面还没法左移，这时播放头自然
从左往右走，走到锚点才开始滚。这是所有 DAW 的标准行为；一味钳住反而会让
开头几秒播放头贴在屏幕中间不动、音轨也不动，看着像卡死。

新增 `followPlayhead(tick)` / `snapToPlayhead(tick)` / `followEnabled`。
手指按住画面平移时不跟随（`userPanning` 标志），否则手指往左拖、画面每帧被
拽回右边，就是"拖不动"的那种手感。停下播放后只更新位置、不动滚动 ——
用户可能正手动画到别处看。

### 3. 每次退出重进多一段音频

**真因 A：补扫投递目录时也往时间线上摆。**

`drainInbox` 走的是 `importAudio` 默认路径，而这个函数默认会把素材
`placeAudio` 到当前选中轨的播放头位置。于是每启动一次、inbox 里还有残留文件
（进程被杀时清理回调没跑到），就在时间线上多摆一块。

**真因 B：完全没有内容去重。**

同一个文件改个名就是新素材，重复导入多少次就有多少条素材在池子里。

**修法：**

1. `importAudio` 增加 `placeOnTimeline` 参数。只有用户主动导入走 `true`；
   `drainInbox` 与 `rescanInbox` 走 `false` —— 补扫的语义是"看看有没有漏掉的
   素材"，不是"往时间线上再糊一块"。
2. `AudioAsset` 新增 `fingerprint`（FNV-1a 64 位内容哈希）。导入时先算指纹，
   池子里有同指纹的直接复用那条素材，不落新文件、不占新缓冲区、也不多摆片段。
   最多扫 65536 个采样点，三分钟的歌也只多几毫秒。
3. **存量清理**：`restoreAudio` 在 reload 之后跑一次 `dedupeAudioAssets()`。
   只修导入路径只能防住"以后不再重复"，用户已经攒下的重复还在工程里 ——
   打开软件照样看到一堆同名素材。合并规则：同一内容保留 id 最小的那条，
   引用旧 id 的片段改指过去，完全重合的重复片段去掉，磁盘上的孤儿文件删掉。
4. `sameContent` 的判据**故意从严**：只认"两边都有指纹且相等"或"路径完全相同"。
   绝不用"帧数 + 采样率"—— 两首时长恰好相同的歌会撞上，合错了是不可逆的
   数据丢失；合漏了只是留着一条多余素材。

## 1.32 更新

### 1. 「更多」改名为「设置」
导航栏与走带条上的按钮文字都改成「设置」，与实际打开的内容一致。

### 2. 设置开关全部无效（真因两条）

**真因 A：开关圆钮永远画在"关"的位置。**

`buildRow` 里是先手写 `checked = row.boolValue`，再调 `setChecked(row.boolValue)`。
而 `setChecked` 开头有一句 `if (checked == v) return` ——
此时 `checked` 已经是目标值，于是直接返回，**弹簧位置（knobSpring）永远停在初始的 0**。
结果：`checked` 是 true，圆钮却画在左边。

下次打开设置时，`boolValue` 从 prefs 读到 true，但圆钮又停在 0 ——
看起来就是"没打开"。这就是反馈里"打开无作用、再打开显示没打开"的完整解释。

修法：`setChecked` 即使在值相同时也要把弹簧位置对齐：

```kotlin
val wasSame = checked == v
checked = v
if (animate && !wasSame) knobSpring.animateTo(target)
else knobSpring.snapTo(target)   // 首次绑定 / 值未变，直接吸附到正确位置
```

**真因 B：四个开关只写配置，不做任何实际动作。**

`dimBackground` / `keepAwake` / `metronome` / `showOrnaments` 的 onToggle
只写了 `settings.xxx = v`，代码里没有任何一处把这些值读回去生效。

新增 `SettingsApplier` 接口，每个开关改变后**立刻调用对应的 apply 动作**：

| 开关 | 实际动作 |
|---|---|
| 背景压暗 | 改 `StudioBackground.dim` 并重绘 |
| 顶部摆件 | 真的 `visibility = VISIBLE/GONE` |
| 节拍器 | `engine.setMetronome()` + 走带条状态 |
| 常亮 | 真正 add/clear `FLAG_KEEP_SCREEN_ON` |

同时每个开关都有 `actualXxx()` 回读**真实生效状态**：打开设置时显示的是真实状态
而不是 prefs 里的值，apply 失败也不会谎报成功。

开关状态机已用独立 Kotlin 程序验过 5 个场景（含两个旧代码会失败的），全部正确。

### 3. 自定义背景图依旧无效（真因三层，逐层算过数）

拿一张中等灰（128/255 = 50%）的图，把整条处理链的乘法算出来：

| 处理层 | 上一版参数 | 结果亮度 |
|---|---|---|
| 原图 | — | 50% |
| ColorMatrix 压暗 | contrast 0.72, offset 26 | 46% |
| 顶部渐变压暗 | 0xB4（71%） | 14% |
| 底部渐变压暗 | 0xCC（80%） | 9% |
| 背景层二次压暗 | 0x4A（29%） | 约 7% |
| **内容区不透明底** | **0xB8（72%）** | **约 9%（全黑）** |

**每一层单看都"合理"，乘起来就是全黑。** 这就是为什么设置提示成功、图也确实存下来了，
但屏幕上什么也看不到。

修正后的参数（目标：内容区外能看到接近原图，内容区内能透出纹理）：

| 处理层 | 新参数 | 说明 |
|---|---|---|
| 去饱和 | 0.60 | 保留照片感，不再灰成一片 |
| 压暗 | contrast 1.0 / offset 0 | 完全不压。这是关键决定 |
| 顶部渐变 | 0x3D（24%） | chrome 区能看清字即可 |
| 底部渐变 | 0x55（33%） | 同上 |
| 背景层二次压暗 | 0x14（8%） | 只作轻微统一 |
| 内容区底 | **0x76（46%）** | 实测平衡点 |

**职责重新划分**：背景图保持接近原图的亮度（用户选它就是因为它好看），
压暗的责任交给内容区自己的半透明底 —— 只压内容区，页面边缘与 chrome 保持原貌。

实测验证：造了一张 1440×2560 的测试图（渐变天空 + 两个亮色块），
用 Python 精确复现 Android 的 ColorMatrix 与各层 alpha 合成，
最终屏幕亮度从 **9% 提到 25.9%**，渐变色带与色块都清晰可辨。

另外补了两处漏掉 `CanvasBackdrop` 的视图：`StepSequencerView` 与 `AutomationView`
（它们仍在画不透明底，会盖掉背景）。

## 1.31.1 更新（启动闪退修复）

**问题**：装上 1.31 后一进软件就闪退。

**崩溃栈**（真机 logcat 实读）：

```
kotlin.UninitializedPropertyAccessException:
    lateinit property content has not been initialized
  at MainActivity.applyBackground(MainActivity.kt:1329)
  at MainActivity.buildUi(MainActivity.kt:252)
  at MainActivity.onCreate(MainActivity.kt:99)
```

**根因**：1.31 为了实现"背景图生效"，在 `buildUi()` 早期（第 252 行，
内容 View 还没创建）调用了 `applyBackground()`，而它内部要
`content?.invalidate()` 并 `refreshAll()` —— 两者都会读 `content` / `rack` /
`playlist` / `piano` / `mixer` / `keys` 这些 `lateinit` 字段。

这里有个 Kotlin 的陷阱值得记下来：

```kotlin
private lateinit var content: FrameLayout
...
content?.invalidate()   // 并不会"安全跳过"！
```

`?.` 只能拦住**值为 null** 的情况。`lateinit` 字段在赋值前读取时抛的是
`UninitializedPropertyAccessException`，那个异常发生在**读取字段的瞬间**，
`?.` 根本没机会介入。正确写法是：

```kotlin
if (::content.isInitialized) content.invalidate()
```

**修法**（三层）：

1. `applyBackground()` 不再调用 `refreshAll()`，改成对每个 `lateinit` 视图用
   `::x.isInitialized` 逐个判断后再 invalidate
2. `applyBackground()` 的调用点从 `buildUi()` 开头移到 `setContentView(root)` 之后 ——
   那时所有视图都已创建，从根本上不会碰到未初始化的字段
3. `onCreate` 整段加 `runCatching` 隔离：任何一步失败都降级成
   "能打开 + 顶部红条说明崩在哪"，而不是让整个应用起不来。
   点红条可看完整堆栈并可复制

**顺带修的两处**：

- `rootLayout?.requestApplyInsets()` —— `rootLayout` 是 `FrameLayout?`（可空而非
  lateinit），`?.` 在这里是对的，保留
- **底部数值表永远不更新**：`refreshPlayhead()` 开头有
  `if (!session.engine.available) return`，把读数条与摆件都挡在后面。
  但这两者只依赖工程数据、不依赖音频引擎（"引擎不可用但界面仍可使用"
  本来就是既有设计）。已把它们的刷新移到引擎判断之前。

## 1.31 更新

### 钢琴引擎：AI 能真的"弹"出来

之前只能"写音符让软件合成"。现在有两层：

- `flowstudio_piano_score` —— 生成演奏音符（进工程后还能改）
- `flowstudio_piano_render` —— 渲染成**真实 WAV**（可导入为音频片段）

渲染器是离线物理建模，不是采样、不是手机音源：音色由引擎决定，
导出的文件在任何播放器里都一样。核心是模态加法合成：

| 要素 | 作用 |
|---|---|
| 弦刚度非谐 `f_n = n·f0·√(1+B·n²)` | 钢琴区别于电子琴的第一特征。B 低音大、高音小 |
| 分音独立衰减 `exp(-(a+b·n))` | 高次分音衰减远快于基频 → 起音明亮、迅速变暖 |
| 击弦位置 1/7 凹陷 | 槌子敲在弦长 1/7 处，第 7 次谐波凹陷。没有它听起来像风琴 |
| 双弦拍频 | 中高音每音 2-3 根弦，微失谐 0.3-0.8 音分 → 钢琴"活"的来源 |
| 击弦噪声 | 槌击的 5-20ms 宽带噪声，是"咔"的质感 |
| 音板共鸣 | 短梳状延迟，让低中频更厚 |
| 力度非线性 | 强奏变亮而不只是变响（高次分音随力度增加） |

三种琴型：`grand`（三角）/ `upright`（立式，余音短、中频厚）/ `rhodes`（电钢琴，带 FM 层）。

演奏生成也不是随机撒音符：
- **左手伴奏型**：柱式 / Alberti 低音 / 分解和弦 / 切分 comping / bossa 3+3+2 / 八度驱动
- **右手织体**：长音铺底 / 八分重复 / 上行琶音 / 稀疏点缀
- **乐句强度曲线**（`arc` / `build` / `anthem` / `bare` / `steady`）：决定每小节的织体密度与力度基准。
  强度 0.25 时右手留白，0.85 时左手换八度驱动 —— 一首曲子不会从头到尾一个密度
- **人性化**：右手时间可抢可拖（±0.22 格），左手几乎不晃（低音是地基）；力度带拍位重音倾向
- **种子可复现**：同 seed 同结果，换 seed 就换一段

实测：8 小节 175 个音，渲染 18.2 秒音频耗时 1.4 秒（13 倍实时）。
FFT 验证 Am 和弦的 A1/A2/A3/C4/E4/A4 六个频率全部在位。

## 1.29 更新

### 音乐空间：三种新乐器 + 五种新效果器

原来只有六种音色，要写吉他分解、弦乐铺底或管风琴只能拿 Synth 硬凑；
效果器十种里缺"能让声音动起来"的那一类。这一版全部补齐，算法都用公开经典实现：

**新乐器**（ordinal 与 C++ 侧严格对齐）

| 乐器 | 算法 | 来源 |
|---|---|---|
| 拨弦 PLUCK | Karplus-Strong 数字波导 | Karplus & Strong, 1983 —— 物理建模的起点，至今仍是拨弦最划算的做法 |
| 弦乐 STRINGS | 三路失谐锯齿合奏 + 颤音 | 弦乐组"厚"的经典做法：微失谐 + 相位错开 |
| 风琴 ORGAN | 加法合成，9 根拉杆 | Hammond 拉杆风琴的谐波配比（0.5/1.5/1/2/3/4/5/6/8 倍） |

拨弦有两处踩过的坑写在代码注释里：**读与写必须落在同一个格子**（否则延迟退化成 1 个样本，
能量全跑到高频去），以及**激励要用棕噪声而不是白噪声**（白噪声让每个泛音一样响，
听起来像弹棉花，还会盖住基频）。另外加了分数延迟补偿，音准误差从几十音分降到 1 音分内。

**新效果器**

| 效果器 | 做法 |
|---|---|
| 电颤 TREMOLO | 正弦/方波/锯齿 LFO 的幅度调制 |
| 自动声像 AUTOPAN | 同 LFO，作用在左右两声道且相位相反，等功率声像 |
| 饱和 SATURATOR | tanh + 非对称项（产生偶次谐波，磁带味；纯 tanh 只有奇次，听着偏硬） |
| 噪声门 GATE | 侧链包络跟随 + 阈值开关 + 起音/释放平滑 |
| 立体声宽度 WIDTH | M/S 处理 + Haas 式伪侧信号（见下）+ 低频保持 |

宽度效果有个非显然的点：**纯 M/S 对单声道素材完全无效**（侧信号本来就是 0，
实测侧信号 0.0454 → 0.0454 一点没变）。所以这里先用两条不同延迟（4ms / 9ms）
的副本造出伪侧信号，再与真实侧信号叠加 —— 单声道素材也能加宽。

引擎自测从 62 项扩到 **80 项**，新增覆盖：三种乐器的基频正确性、五种效果器
"输出确实被改变"、电颤的峰值因数升高、宽度的侧信号增强、饱和的二次谐波增加。

### 顶部摆件

导航栏中段在宽屏上是纯色。这一版放了三个不接收触摸的小装置（`ui/OrnamentBar.kt`）：

1. **立体声电平**：两根细柱跟主输出峰值起伏，绿→黄→红分档，带峰值保持线。
   这是唯一"有用"的一个 —— 扫一眼就知道有没有声音。
2. **磁带卷盘**：播放时按约 3 秒一圈转，停止时停住。
3. **唱针臂**：播放时落到唱片上，停止时收回，角度做平滑过渡。

三者都是 Canvas 直接绘制，无图片资源、无动画框架。**静止时不请求下一帧** ——

### 插件：音频内容识别

新工具 `flowstudio_analyze_audio`：判断一段音频是人声、钢琴、吉他、贝斯、鼓、
弦乐铺底、管乐、合成器还是音效，并给出"放哪条轨、用什么乐器、怎么处理"。

不是黑盒模型，全部特征可解释：

- **解码**：ffmpeg → 单声道 44.1kHz（用 44.1k 不是 22.05k：高次谐波在 22.05k 下会折返，
  伪造出并不存在的基频 —— 实测一段 f0=180Hz 被读成 325Hz）
- **频谱**：自写 radix-2 FFT，提质心、滚降、平坦度、低/中/高频带比、
  1/3 倍频程频段能量
- **音高**：NSDF（McLeod & Wyvill，YIN 的前身）+ 分数延迟 + 倍频校正，
  9 个音高（82-880Hz）实测误差全部 < 1 音分
- **判别用的三个关键量**（都是踩坑后找到的）：
  - `midCoverage` 中频覆盖度：人声的共振峰是**连续一片**，锯齿波只有孤立的谐波峰
  - `midPeakiness` 中频尖峭度：谐波列（峰值/中位数大）vs 连续型频谱
  - `envDynamics` 包络动态：打击类方差大，持续类方差小
- **规则分类**：每条规则给 0..1 分，取最高；含反证项（"谐波性极强说明是乐音不是鼓"、
  "低频占比极高说明是贝斯不是弦乐"、"谐波性接近 1 说明是振荡器不是真拨弦"）
- **置信度**是"领先优势"，低于 0.15 明确说"不确定"并列出候选

验证：程序生成的五类标准素材（钢琴/贝斯/鼓/弦乐/人声）**5/5 全对**；
真实人声素材判为人声（置信度 0.50）。

## 1.22.1 更新

- **修闪退**：`ArrayIndexOutOfBoundsException: length=361; index=361 @
  PlaylistView.drawNoteEnvelope`。根因是包络缓存 key 写成了 `clip.id * 31 xor cols`，
  把片段 id 和像素列数混进同一个数值空间 —— 片段 1 宽 97 列与片段 2 宽 64 列会算出
  同一个 key（126），拿到的是别的长度的数组，按当前列数循环就写越界。
  现在改成带长度的复合 key，并在绘制时再按数组实际长度兜一层。
  同样的输入空间下，旧写法的碰撞组合超过 10 万组，新写法零碰撞。
- 缓存 key 里加入了起点、长度、素材偏移：拖动或裁剪片段后包络会重算，
  不再停在旧位置。
- 缩放后整批清缓存的条件从 `bw.toInt()` 改成直接比较原始浮点值，
  避免两个接近的缩放比被截断成同一个整数而漏清。
- **状态面板不再误报**：音频流是**按需启动**的，没按播放时本来就不开流。
  以前「audioStream / render / signal」三项会同时标 ✗，看着像坏了。
  现在分成待机与失败两态，待机时标 ✓ 并写明「按需启动，按播放才开流」；
  只有「在播却没流」才真的报错。
- **播放失败不再假装成功**：`play()` 以前无条件 `play()` 并点亮播放键，
  即使 `startAudio()` 失败也照样走位置、照样没声音。现在返回布尔值，
  界面在流起不来时保持停止态并明确提示原因。
- 桥接 `/transport/play` 区分两种失败：主线程调度不上回 503，
  调度上了但流起不来回 200 + `warning`，避免插件重试一个重试也解决不了的错误。
- CI 增加静态检查：禁止把列数 `xor` 进缓存 key，实测能抓住回退。

## 架构

引擎和界面彻底分离，这是必须的：音频线程一次 GC 停顿就是一声爆音。


## 功能

**编排**
- 步进器：16 分网格，拖动刷格子
- 钢琴卷帘：画、拖、拉长、改力度、量化、框选删除
- 播放列表：片段拖动、跨轨移动、拉长、循环区间
- 样式（Pattern）制，跟 FL 一样解耦轨道与样式

**音源**（全部实时合成，不含采样文件）
- 3 振荡器减法合成器（PolyBLEP 抗混叠）
- 减法贝斯
- 鼓组：8 类打击，底鼓带音高下滑
- FM 钟琴 / FM 电钢（带立体声颤音）
- 采样器（WAV 导入）

**效果**（每轨 4 个插入槽 + 2 条发送总线）
滤波、节拍同步延迟、Freeverb 混响、合唱、失真、压缩、6 段均衡、降位、移相

**混音**
- 每轨：推子、等功率声像、静音、独奏、电平表
- 母带：音量、前馈限幅、软削波、增益
- 自动化：包络曲线，编辑所见即所得

**其它**
- 后台播放（前台服务）
- 导出 16-bit 立体声 WAV，走系统分享
- 工程存档 JSON，自动保存

## 已知边界

- 只打了 `arm64-v8a`。要给 x86_64 模拟器跑，改 `build.gradle.kts` 的 `abiFilters`。
- 采样器只解 8/16/24/32-bit PCM 与 32-bit float 的 WAV。
- 自动化曲线是线性插值，不是贝塞尔。
- 录音（麦克风输入）留了权限和接口，尚未接线。
